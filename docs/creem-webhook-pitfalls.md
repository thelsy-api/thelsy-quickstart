# 用 Creem 做自动发货：两个只有真实付款才会暴露的坑

**场景**：Creem（Merchant of Record）收款 → 自建 webhook → 自动建号 / 加额度 / 发交付邮件。
测试环境跑通不代表生产跑通。下面两条都是**真实付款第一次进来时才暴露**的，而且都不报错。

> 本文的代码均为**示意实现**，不是可直接运行的完整代码。

---

## 坑 1：首笔订阅会在**同一秒**发两条事件 → 同一笔钱加两次额度

### 现象

第一笔真实付款是 $19 的月度订阅，客户实际到账 **19,500,000** 额度，而正确值应该是 **9,750,000**。
**系统没有报任何错**——两条事件都合法、签名都对、都该被处理。

### 原因

Creem 在**首笔订阅**成功时会同时发出两条事件：

| 事件 | 说明 |
|---|---|
| `checkout.completed` | 结账完成 |
| `subscription.paid` | 订阅已支付 |

**两者的 `event_key` 不同。** 所以"按 `event_key` 去重"这个最直觉的做法完全失效——它们是两条不同的
事件，各自都会走到加额度那一步。（据我们观察，续费月份通常只来一条，这就是为什么这个现象只在**首笔**出现。）

### 解法：三层幂等，缺一不可

**第 1 层：记账列 `credited_at`**

不要在"事件是否处理过"上做判断，要在"钱是否已经记过账"上做判断。加额度成功的那一刻，把时间戳写进这一行：

```sql
CREATE TABLE entitlements (
  id          INTEGER PRIMARY KEY,
  email       TEXT NOT NULL,      -- 统一小写后再入库
  plan_amount TEXT NOT NULL,      -- 该档位应加的额度，例如 '9750000'
  credited_at TEXT,               -- 加额度成功那一刻写入；NULL = 还没加
  last_event  TEXT,               -- 最近一次触发的事件 key
  created_at  TEXT NOT NULL
);
```

**第 2 层：跨事件去重（关键）**

不按 `event_key` 判重，而是按**业务特征**判重：

```
同一笔付款 ≈ 邮箱（不分大小写） + 档位额度 + 一个足够长的时间窗（本文取 60 分钟）
```

```python
# 示意：在加额度之前先抢锁
row = SELECT * FROM entitlements
      WHERE lower(email) = lower(?) AND plan_amount = ?
        AND created_at > now_minus_60_minutes
      ORDER BY id DESC LIMIT 1

if row and row["credited_at"]:
    log("同一笔付款的重复事件，已跳过加额度")
    return 200          # 必须回 200，否则 Creem 会一直重试
```

**第 3 层：同一事件的重复投递**

`event_key` 已处理过 → 直接返回 `200`，不要重复执行任何副作用。

### 验证方法（别只看测试环境）

上线后用**真实签名**的回调重放一次同一条事件，确认：
1. 日志出现「同一笔付款的重复事件，已跳过加额度」；
2. 额度**只增加了一次**。

> 经验：把幂等键落在**数据库的唯一约束**上，而不是进程内存里。webhook 会被重试、会被并发投递，
> 内存去重在重启和并发下都会失效。

## 坑 2：生产环境标识是 `prod`，不是 `live`

这个坑的可怕之处在于**它不报错**。

如果你的处理逻辑写成 `if payload["mode"] != "live": return`（本项目读到的环境标识字段就是 `mode`，而很多支付平台的惯例取值是 `live`），
那么**每一笔真实付款都会被静默丢弃**——客户付了钱，你没发货，而且日志里一片安静。

**上线前必做**：用一笔真实小额付款走完整链路，确认"付款 → 建号 → 加额度 → 收到邮件"。

## 附带：后台「发送测试事件」的假客户不好过滤

Creem 后台可以手动发送测试事件，用来验证 webhook。但它的假客户**邮箱域名不固定**——
至少见过 `customer.creem.io` 和 `creem.io` 两种，而且环境标识同样是 `prod`、**签名也是合法的**。

所以不要用 `mode` 或签名去区分测试与真实流量，只能按 `creem.io` 这个**后缀**拦截。
建议把这类事件单独记一行日志，方便日后排查"为什么多了一个假账号"。

---

## 退款与取消订阅事件

`refund.created` 和 `subscription.canceled` 两个事件都会正常送达。

**建议只记日志 + 发告警，不要自动撤销额度。** 退款可能对应线上纠纷、部分退款或客户重新订阅，
自动扣减很容易造成误伤；人工确认后再处理，代价远小于出错。

---

## 一句话总结

**webhook 的正确性不取决于"事件有没有收到"，而取决于"同一笔钱会不会被记两次账"。**
把幂等设计在业务语义上（邮箱 + 档位 + 时间窗），而不是设计在事件 ID 上。
