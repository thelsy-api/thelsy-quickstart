# 用 New API 做 SaaS 自动开户：四个只会被真实流量撞出来的坑

**场景**：自建 AI API 网关（New API）→ 客户付款 → webhook 自动建号 / 加额度 / 发 API Key。
接口看起来是标准的 CRUD，但有几个字段的**实际行为与直觉相反**，而且大多不报错。

> 本文代码均为**示意实现**。接口行为以你所用版本的源码为准（本文对应 `model/user.go` 的 `EditWithTx`）。

---

## 坑 1：`PUT /api/user/` 只能写四个字段 —— 用它改额度是**无效**的

直觉做法是"改用户 = PUT 用户对象，把 `quota` 一起传进去"。**不生效。**

`EditWithTx` 实际只写这四个字段：

```
username / display_name / group / remark
```

→ 传了 `quota` 也不会有任何反应，**而且不报错**（返回值看起来是成功的）。

**正确做法**：额度必须走管理接口做**原子自增**：

```
POST /api/user/manage
{
  "id": 123,
  "action": "add_quota",
  "value": 9750000
}
```

> 不同小版本的字段略有差异，请对照你所用版本的接口文档确认字段名。

**并且注意**：同一条 `PUT /api/user/` 里**不传 `group` 会被写成空串**。结果就是客户拿到 Key 后立刻报
`No available channel`——因为他的分组没了。

> 结论：改额度走 `manage`，改资料走 `PUT`，**两者不要在同一个"保存用户"动作里混做**。

---

## 坑 2：`email` 也写不进去 → 客户**无法自助找回密码**

同一个 `EditWithTx` 的限制。后果比看起来严重：

- 客户账号里没有邮箱；
- "忘记密码"功能形同虚设（发不出去，因为账号上没有收件地址）；
- 你只能人工重置，客户每次都要来找你。

**如果你要做成 SaaS**，需要在外层自己维护一张「邮箱 → 账号」的映射表，并且：
1. 交付邮件里明确写清"密码重置请联系支持"；
2. 把人工重置做成一个 SOP，而不是每次临时处理。

---

## 坑 3：建令牌只能给"当前登录用户"建

`AddToken` 的语义是"给**当前登录用户**创建令牌"。

所以**"管理员直接替客户建一个 Key"这件事做不到**。自动发货的流程必须绕一圈：

```
管理员建号  →  以该客户身份登录  →  建 Key  →  登出
```

设计自动发货时请把这一步按这个顺序实现，否则会在"建 Key"这一步卡住很久。

---

## 坑 4：⚠️ 自带的支付模块务必关闭

New API 自带的 Stripe / Creem 支付模块，在**密钥为空**的情况下会**放行伪造的回调**。
该类风险**已于 2026-04 被公开披露**。

**建议**：
- 若你不用它的支付模块，**保持关闭**；
- 用外部请求验证一下回调路径确实返回 `403`（而不是 200），确认它真的关掉了；
- 若要用它，务必把密钥配好并自行做签名校验，不要依赖默认行为。

> 如果你要自己写 webhook，可参考 [Creem 自动发货的两个坑](creem-webhook-pitfalls.md)。

---

## 顺带一个（不属于 New API，但一定会撞上）：客户端用自己的默认模型名

Codex CLI、Cursor 这类客户端**不会用你配的模型名**，它们会发自己的默认模型名（例如 `gpt-6-astra`）。
网关没有这个模型，就直接返：

```
503 No available channel for model 'xxx' under group default
```

**解法**：渠道编辑 →「模型映射」填 `{"客户端模型名":"你的真实模型名"}`，
**并且把别名也加进该渠道的「模型」列表**（网关会弹窗提示，点「添加后提交」即可）。

只填映射、不加进模型列表，一样不生效——这是最容易漏的一步。

---

## 一句话总结

**这四个坑的共同点是"不报错"**：接口返回成功、日志干净、但业务是错的。
做自动开户时，每一个写操作都要**端到端验证一次**（真的建出号、真的加上额度、真的能用 Key 调通），
不要相信返回值。
